# Контекст проекта — для Claude Code

Конспект для продолжения работы в новом чате. Проект спроектирован в claude.ai,
затем несколько больших сессий в Claude Code довели его до текущего состояния.

## Что это за проект

Веб-версия личного трекера трат (наследник telegram-expense-bot) — PWA для
iPhone («Добавить на экран Домой»), с мгновенным streaming-распознаванием
голоса и работающая офлайн. UI копирует референс-приложение «Qalta»
(пользователь присылает скриншоты/видео из него и просит повторять 1:1,
вплоть до покадрового разбора анимаций).

- Репозиторий: `github.com/Esenzhan/expense-web` — монорепо: `frontend/`,
  `backend/` **и `bot/`** (Telegram-бот, см. «Telegram-бот» ниже; у бота
  никогда не было отдельного репозитория — `expense-bot` на GitHub не
  существует, локальный `.git` в его исходной папке указывал в никуда)
- Прод фронтенд: `https://expense-web-eosin.vercel.app` (Vercel, аккаунт
  `esenzhan`, scope `tommili1`, проект **`expense-web`** — см. предостережение
  про `vercel link` ниже)
- Прод бэкенд: `https://expense-web-peo6.onrender.com` (Render free tier,
  автодеплой из GitHub `main`). На Render в том же workspace есть ещё один,
  **не связанный** сервис с именем `expense-bot` (Python, сломанный деплой,
  не используется) — не путать при добавлении env-переменных, проверять по
  URL/типу сервиса, не по названию
- БД: Neon Postgres (проект `expense-web`)
- Вход на сайт: Google OAuth, закрытый список из 2 аккаунтов (см. раздел
  «Мульти-аккаунт» ниже)

## Стек и архитектура

```
iPhone PWA (standalone, офлайн-способный через sw.js)
  │ MediaRecorder webm/opus, чанки 250мс
  │ (клиент буферизует чанки до открытия WS + 700мс на рукопожатие
  │  сервер→Deepgram; первый чанк несёт заголовок контейнера!)
  ▼
WebSocket wss://…/ws/voice   ← при «стоп» клиент шлёт {"type":"stop"}
  │ реконнект-цикл ~80с если сокет не открылся (Render просыпается 30–50с)
  ▼
Deepgram streaming STT (language=ru, nova-2, interim_results, endpointing=500)
  │ partial → на фронт live; сервер тоже буферизует аудио до открытия DG-сокета
  │ стоп-маркер ИЛИ авто-финал (500мс тишины) → сервер сразу отпускает микрофон
  ▼
Claude Haiku (claude-haiku-4-5-20251001) парсит текст → {amount, category,
  wallet, description}; списки категорий и кошельков подставляются в промпт
  ИЗ БД (кэш 60с, инвалидация при изменениях)
  ▼
Сервер шлёт {type:"parsed", proposal} — НЕ сохраняет сам!
  ▼
Фронт показывает карточку подтверждения (Отмена/Сохранить) → POST /api/expenses
  (офлайн: POST падает → трата уходит в localStorage-очередь, синкается
  когда появится сеть — см. офлайн-раздел ниже)
```

- **Backend** (`backend/src`): Express + ws + pg + Anthropic SDK + googleapis,
  один процесс. Таблицы: `users` (по одной строке на Google-аккаунт из
  allowlist — email/name/google_sub/зашифрованный google_refresh_token/
  sheet_id/bot_api_key), `expenses` (теперь с `user_id`), `categories`
  (seed 10 штук на КАЖДЫЙ кошелёк — см. «Категории per-wallet» ниже,
  больше не единый общий список), `wallets` (seed: Личные/Семья/Бизнес/
  Ремонт; «Личные» — фолбэк, защищён; у каждого кошелька теперь есть
  `shared` — см. «Мульти-аккаунт» ниже), `category_limits` (см. «Лимиты
  по категориям» ниже). Роуты: `/api/auth/google/{start,
  callback}` + `/api/auth/me`, `/api/expenses` (GET с
  `?wallet=&from=&to=&limit=&q=` — `q` полнотекстовый поиск по
  description/category/amount, см. «Поиск» ниже / POST — принимает
  опциональный `created_at` для бэкфилла исторических трат с реальной датой
  вместо `now()` / PUT / DELETE — все требуют auth), `/api/stats/{by-wallet,
  daily}` (все требуют auth; **`/api/stats/summary` УДАЛЁН** — фронт больше
  не дёргает его, шапочный итог теперь читается из `insights.total`, см.
  «Экраны и фичи» → Главная), `/api/categories`
  (GET публичный, принимает `?wallet=` — без него отдаёт ВСЕ категории
  всех кошельков с полем `wallet` в каждой строке, для одноразовой
  гидратации фронта и обратной совместимости; бот тоже дёргает, теперь
  всегда с `?wallet=`; POST/DELETE только с логином, DELETE теперь
  `/api/categories/:wallet/:name`), `/api/wallets` (аналогично; PUT
  переименовывает и переносит траты транзакцией; DELETE блокируется при
  наличии трат — теперь есть в UI, см. «Экраны и фичи» → Счета),
  `/api/category-limits` (все требуют auth — см. «Лимиты по категориям»
  ниже). **`/api/stats/insights` УДАЛЁН** — вся логика Инсайтов
  переехала на фронт (см. ниже), держать две реализации арифметики в синхроне
  оказалось лишним.
- **Frontend** (`frontend/src`): React + Vite, без UI-библиотек, стили в одном
  `styles.css`. Recharts УДАЛЁН — единственный график (Инсайты) нарисован
  вручную SVG (`InsightsChart.jsx`). Реестры категорий/кошельков —
  модульные сторы (`categoryIcons.js`, `wallets.js`) с hydrate из API +
  localStorage-кэш. `insights.js` — портированная 1:1 с бэкенда чистая
  арифметика (`computeInsights`, `periodRange`), теперь единственная копия.

## Мульти-аккаунт: Google-логин + шаринг кошельков (добавлено 2026-08-12)

Раньше сайт был однопользовательским (один общий Postgres на всех), а
Telegram-бот писал напрямую в Google Sheets — **две независимые базы**.
Теперь всё объединено: закрытый логин на сайте (2 аккаунта), бот пишет
через API сайта, обе стороны сходятся в одних и тех же данных.

- **Вход**: Google OAuth (`backend/src/routes/auth.js`,
  `services/googleAuth.js`), allowlist по email в env `ALLOWED_EMAILS`
  (только вы двое — открытой регистрации нет). Scope запрашивает не только
  identity, но и `spreadsheets`+`drive.file` — токен нужен бэкенду, чтобы
  писать в личный Sheet пользователя даже когда его нет на сайте (например
  когда трату шлёт бот). `prompt=consent` всегда форсит выдачу
  `refresh_token` (иначе Google отдаёт его только при самом первом
  согласии). JWT-сессия живёт 180 дней, хранится во фронте в
  `localStorage` (`traty-token`, см. `frontend/src/auth.js`), шлётся как
  `Authorization: Bearer`.
- **Личная Google-таблица**: при первом логине (`ensureUserSheet` в
  `services/sheets.js`) от имени пользователя создаётся Spreadsheet в ЕГО
  СОБСТВЕННОМ Google Drive (не в сервисном аккаунте) — `sheet_id`
  сохраняется в `users`. Формат листов 1:1 с тем, что раньше писал сам бот
  (`bot.py`'s `get_wallet_sheet`): вкладка на кошелёк, шапка `Дата, Время,
  Сумма, Категория, Описание, Источник, Кто, ID` — колонка `ID` (Postgres
  `expenses.id`) добавлена НОВОЙ, бот её не читает, но по ней бэкенд находит
  строку для update/delete.
- **Общие vs личные кошельки** (`wallets.shared`, boolean): Семья/Бизнес/
  Ремонт = `true`, Личные = `false`. Это работает НА ДВУХ уровнях
  одновременно:
  - **Сайт** (`routes/expenses.js`, `routes/stats.js`): траты общего
    кошелька видны и суммируются для ОБОИХ аккаунтов (`WHERE user_id=$me
    OR wallet = ANY(shared_names)`); личные — только у создателя. НО
    редактировать/удалять может только тот, кто СОЗДАЛ трату, даже в общем
    кошельке — чужая строка в `ExpenseList` рендерится с классом
    `.readonly` (тусклая, `pointer-events` не блокируются CSS, но клик
    просто не открывает `onSelect`) и бэкенд отдаёт 404 на чужой
    PUT/DELETE (сделано намеренно так — см. `[[dariya-workflow]]` про
    итеративные уточнения).
  - **Sheets**: общая трата зеркалится СРАЗУ в обе личные таблицы (кто бы
    её ни залогировал), с колонкой «Кто» = имя автора. Личная — только в
    таблицу автора, «Кто» пусто. Это заменило собой старый
    `RENOVATION_OWNER_EMAIL`-костыль (принудительная запись Ремонта в одну
    конкретную таблицу) — теперь это просто частный случай «Ремонт тоже
    shared», спец-код убран.
- **Бот** (`bot/bot.py`, живёт в этом же репо, деплой — см. ниже):
  `/addcategory` и `/deletecategory` УДАЛЕНЫ — категории только с сайта.
  Бот получает список категорий через `GET /api/categories` (кэш 60с),
  сохраняет трату через `POST /api/expenses` с заголовком `X-Bot-Key`
  (постоянный ключ на аккаунт, `users.bot_api_key`, сопоставлен с
  `USER1_TELEGRAM_ID`/`USER2_TELEGRAM_ID` в `.env` на VM — **однажды уже
  перепутали местами**, симптом был «сообщения Есенжана улетают в таблицу
  Дарии и наоборот», чинится свапом `USER1_BOT_KEY`/`USER2_BOT_KEY`).
  `/budget` и `/renovation` НЕ ТРОГАЛИ — по-прежнему читают Google Sheets
  напрямую через `gspread`+сервисный аккаунт (`GOOGLE_CREDENTIALS_FILE`),
  просто теперь эти таблицы заполняет бэкенд сайта, а не сам бот.
- **Postgres-миграция**: старая (тестовая, однопользовательская) история
  трат была намеренно стёрта (`TRUNCATE expenses`) при добавлении
  `user_id NOT NULL` — см. `initSchema()` в `db.js`, идемпотентно проверяет
  наличие колонки перед труном, повторно не сработает.
- **Env, которые добавились** (см. `backend/.env.example`):
  `GOOGLE_OAUTH_CLIENT_ID/SECRET/REDIRECT_URI`, `ALLOWED_EMAILS`,
  `JWT_SECRET`, `TOKEN_ENCRYPTION_KEY` (шифрует `google_refresh_token` в
  БД, AES-256-GCM, `services/crypto.js`). `RENOVATION_OWNER_EMAIL` больше
  не используется кодом (Ремонт и так shared), но может остаться висеть в
  Render — безвредно.
- **OAuth consent screen**: проект `adept-parsec-500611-h1` в Google Cloud
  (тот же, где сервисный аккаунт бота). Поле для test users в старом UI
  Google Auth Platform — это chip-input, для нескольких email нужно
  добавлять по одному с Tab/Enter между ними, а не через запятую одной
  строкой (иначе примет как один невалидный email).
  **С 2026-08-28 Publishing status = Production** (раньше был Testing —
  см. подробный разбор инцидента ниже, "invalid_grant / протухшие
  токены"). Держать его именно в Production обязательно — это не
  косметика.

## Категории — свой список на каждый кошелёк (добавлено 2026-08-12)

Раньше `categories` был ОДНИМ общим списком на все 4 кошелька. Теперь у
каждого кошелька независимый список (можно добавлять/удалять категории в
одном, не трогая остальные).

- **Схема**: `categories.wallet TEXT NOT NULL REFERENCES wallets(name)
  ON DELETE CASCADE ON UPDATE CASCADE`, уникальность теперь `UNIQUE
  (wallet, name)` вместо `UNIQUE(name)`. `ON DELETE/UPDATE CASCADE`
  обязательны — без них удаление или переименование кошелька падало бы
  500-й (FK violation), так как `routes/wallets.js` не чистит/не
  переносит категории вручную.
- **Миграция прод-данных**: старые общие категории разведены по всем 4
  кошелькам (каждый получил свою независимую копию исходных 10). Мигратор
  в `initSchema()` (`db.js`) **обязательно в транзакции** (`pool.connect()`
  + BEGIN/COMMIT/ROLLBACK, не отдельные `pool.query()`) — первая версия
  была НЕ транзакционной, дропала старый `UNIQUE(name)` ПОСЛЕ попытки
  разложить категории по кошелькам, поэтому падала на первой же вставке
  дубликата имени и роняла бэкенд НА КАЖДОМ старте (прод реально полежал
  в этом состоянии несколько минут). Детект «миграция не завершилась» —
  по `is_nullable` колонки `wallet` (NOT NULL выставляется только в конце
  успешной миграции), не просто по её наличию — иначе повторный старт после
  сбоя решил бы, что мигрировать уже не нужно, и застрял бы в разбитом
  состоянии навсегда.
- **Бэкенд**: новый `backend/src/categories.js` (кэш 60с, по образцу
  `wallets.js`) — `categoryNamesFor(wallet)`, `isValidCategory(wallet,
  name)`, `categoryNamesByWallet()`. Голосовой парсер (`parseExpense.js`)
  теперь в ОДНОМ вызове Claude передаёт карту «кошелёк → его категории» и
  просит модель выбрать категорию именно из списка выбранного кошелька;
  фолбэк при несовпадении — «Прочее» ЭТОГО кошелька, не общее.
- **Бот** (`bot/bot.py`, задеплоен на VM): `get_categories(wallet)`
  дёргает `GET /api/categories?wallet=` с уже определённым через
  `detect_wallet()` кошельком (раньше был один глобальный список +
  хардкод `WALLETS` только для «Ремонт»); хардкод остался как чисто
  офлайн-фолбэк на случай недоступности сайта.
- **Фронт**: `CategoriesSheet` получил переключатель кошельков (вкладки
  сверху, независимо от того, какой кошелёк выбран на главном экране) и
  удаление категории (тап → «✕» → «Точно?» → тап ещё раз; «Прочее»
  защищено). `categoryIcons.js` хранит реестр как `{ [wallet]: [...] }`,
  `listCategories(wallet)`/`getCategoryIcon(wallet, name)` требуют
  кошелёк первым аргументом — при добавлении нового места, где рисуется
  иконка категории, не забывать передавать его (легко забыть и получить
  иконку не того кошелька). Карусель категорий в `EditExpenseSheet`
  пересобирается и перецентровывается при смене кошелька в `<select>`.
- **Иконки** (`CategoryGlyph.jsx`): было 10 глифов (только сид-категории),
  теперь ~78 — покрыт КАЖДЫЙ emoji из пикера `NewCategorySheet`
  (`ICON_GROUPS`), плюс сам пикер и «Рекомендации» (было «Suggestions»)
  теперь тоже рисуют `CategoryGlyph`, а не сырой emoji — выбор в UI сразу
  выглядит так же, как сохранённая категория. При добавлении новых иконок
  проверять НЕ в маленьком превью (32px не показывает реальную форму —
  так пицца без корочки выглядела ровным треугольником, а баг с лишним
  `H`-командой в пути скутера был не виден вовсе), а рендерить каждую
  ОТДЕЛЬНО крупно (150px+) через временный харнесс — см. «Как тестировать
  без телефона». Мелкие окружности (r ≲ strokeWidth) поверх другого
  пересекающегося пути визуально сливаются в кляксу вместо кольца — так
  сломались колёса скутера, наложенные на линию палубы.

## Переименование категории (добавлено 2026-08-28)

Форма «Редактировать категорию» (`NewCategorySheet` в режиме `initial`)
раньше держала поле названия `disabled` — теперь имя правится наравне с
иконкой и цветом, и все прошлые траты этой категории переезжают вместе с
ним.

- **Одна транзакция** в `PUT /api/categories/:wallet/:name`
  (`routes/categories.js`, `pool.connect()` + BEGIN/COMMIT/ROLLBACK):
  строка `categories` → `expenses.category` (обычный TEXT без FK, поэтому
  явный UPDATE) → JSON-снапшоты в `sheets_sync_jobs` (иначе уже стоящая в
  очереди джоба зеркалировала бы в таблицу СТАРОЕ имя уже после ренейма).
  `category_limits` едет сам — у него FK с `ON UPDATE CASCADE`.
- **Google Sheets намеренно НЕ переписываются.** Приложение не читает
  текст категории из таблицы обратно (строка ищется по колонке ID), а
  перезапись — это ~6 запросов к Google на каждую трату при квоте порядка
  60 записей в минуту: ренейм категории с парой сотен трат гарантированно
  ловит 429 и забивает очередь обычным тратам. В таблице имя правится
  руками (решение Дарии 2026-08-28). Телеграм-бот, который читал оттуда
  «Категорию» для `/budget`, из эксплуатации выведен и больше не
  учитывается.
- **`category_renames` — форвардинг старых имён** (`wallet, type,
  old_name, new_name`, уникальный по первым трём). Ренейм не долетает до
  всех клиентов мгновенно: офлайн-очередь, слитая после переименования,
  телефон второго аккаунта с закэшированным списком, вкладка, открытая до
  ренейма — все шлют старое имя, а `expenses.js` молча ронял такие траты в
  «Прочее» (тот же фоллбэк, что и для реально несуществующей категории).
  Теперь оба маршрута трат ходят через `resolveCategoryName()`
  (`categories.js`) — единственное место, где решается, в какую категорию
  на самом деле упадёт запись. Цепочка A→B→C перенацеливает и алиас A;
  переименование обратно удаляет самоссылку; создание категории со старым
  именем снимает алиас на него.
- **Коллизия → 409, слияния нет.** `UNIQUE (wallet, name)` не учитывает
  `type`, так что 23505 ловится и на переименовании расходной категории в
  имя доходной. Слить две категории ренеймом нельзя намеренно: это
  необратимо и слишком легко получается опечаткой — если понадобится,
  делать отдельной явной кнопкой «Объединить».
- **Фронт после ренейма**: `App.jsx` сравнивает возвращённое имя с прежним
  и, если оно изменилось, сбрасывает фильтр списка (его ключ —
  `${type}:${name}`) и дёргает `refreshAll` — загруженные траты держат в
  себе старый текст категории.

## Лимиты по категориям (добавлено 2026-08-13)

Месячный лимит на КАЖДУЮ категорию (не только на весь кошелёк, как раньше в
Инсайтах) — задаётся и виден в шторке Инсайтов, раздел «Лимиты по
категориям» (виден только при периоде «Этот месяц»; выбор другого периода
эту секцию скрывает, лимиты — всегда месячные).

- **Схема**: новая таблица `category_limits` (`wallet`, `category`,
  `user_id` nullable, `monthly_limit`), FK `(wallet, category) REFERENCES
  categories (wallet, name) ON DELETE/UPDATE CASCADE` — переименование или
  удаление категории автоматически чистит/переносит её лимит. `user_id
  IS NULL` = лимит общий (для shared-кошельков — Семья/Бизнес/Ремонт, один
  на обоих); `user_id = чей-то` = личный (для «Личные», каждый свой) —
  та же развилка shared/private, что и у видимости трат. `NULL` не
  уникален в Postgres (`UNIQUE` его не ловит), поэтому «один общий лимит
  на категорию» держится ДВУМЯ частичными индексами (`WHERE user_id IS
  NULL` / `WHERE user_id IS NOT NULL`), не одним обычным `UNIQUE`.
- **Бэкенд**: `routes/categoryLimits.js` — GET/PUT/DELETE
  `/api/category-limits/:wallet/:category`, сам решает shared/private по
  `sharedWalletNames()` и ставит `user_id` соответственно. `PUT` —
  upsert через `ON CONFLICT (...) WHERE ...`, таргетящий нужный из двух
  частичных индексов (два разных SQL-запроса на shared/private случай, не
  один общий).
- **Фронт**: остаток по категории считается КЛИЕНТСКИ — `insights.js` в
  `computeInsights` вернул `categoryTotals` (сумма по категории за уже
  загруженные строки периода), лимиты подгружаются отдельным запросом при
  открытии Инсайтов. Первой строкой в списке — «Весь кошелёк»: сумма
  расходов и сумма ВСЕХ выставленных лимитов по кошельку целиком, плашка в
  цвете `--accent`/`--on-accent` (не как обычная категория) — см. «Тёмная
  тема» ниже: это чёрная плашка с белой полосой в светлой теме, но
  ИНВЕРТИРУЕТСЯ в тёмной (светлая плашка, тёмная полоса), т.к. `--accent`
  сам меняется по теме. Полоса прогресса красится в `--on-accent`, не
  напрямую в белый — на тёмном фоне (до 2026-08-14 там был жёстко `--ink`)
  полоса сливалась с плашкой и была не видна, эта ловушка уже была поймана
  один раз ещё до того, как вообще появилась тёмная тема.
- **onlyMine-баг** (2026-08-14, см. «Только мои» в «Экраны и фичи»): суммы
  и `spent` по каждой категории здесь считаются из `data.categoryTotals`
  (`computeInsights`), который раньше случайно резался тумблером «Только
  мои» — на общих кошельках лимит показывал только половину реальных трат.
  Пофикшено, но если снова увидите, что «Весь кошелёк»/категория показывает
  подозрительно мало при включённом тумблере — это тот самый класс бага.
- **Не путать с** `/budget` в Telegram-боте — это ДРУГАЯ, полностью не
  связанная система лимитов (Google Sheets, вкладка «Лимиты»,
  `DEFAULT_LIMITS` в `bot.py`), появилась раньше и её не трогали. Лимит,
  заданный в Инсайтах на сайте, НЕ виден боту и наоборот — если пользователь
  спросит «почему бот показывает другой остаток», это не баг, это две
  разные системы.

## Тёмная тема (добавлено 2026-08-14)

Настройки → Тема: Системная / Светлая / Тёмная (`ThemeSheet.jsx`). Тёмная —
почти чистый чёрный (`--bg: #0a0a0c`), выбран из трёх мокапов (OLED-чёрный /
тёплый графит / полуночный мятный — пользователь выбрал первый), не
дефолтный «тёплый серый».

- **Хранение**: `localStorage` (`traty-theme`, ключ читается СИНХРОННО в
  `main.jsx` до первого рендера — `applyTheme()`/`theme.js`, чтобы не было
  мигания неправильной темой) + аккаунт (`users.theme`, `GET /api/auth/me`
  возвращает поле, `PUT /api/auth/theme` его меняет). Синк с аккаунта в
  локальный — ОДИН раз при первом `fetchMe()` за сессию (`themeSyncedRef` в
  `App.jsx`), не на каждый рефреш `user`, иначе может затереть смену темы,
  сделанную только что локально, пока старый `fetchMe()` ещё летит.
  «Системная» — `data-theme` НЕ ставится вообще, работает чистый
  `prefers-color-scheme`; явный выбор — `data-theme="light"/"dark"` на
  `<html>`, перебивает медиа-запрос в обе стороны (три блока в
  `styles.css`: голый `:root`, `@media (prefers-color-scheme: dark)`,
  `[data-theme="dark"]`/`[data-theme="light"]`).
- **`--accent`/`--on-accent`** — НОВАЯ пара токенов, отдельная от `--ink`.
  До тёмной темы `--ink` служил и текстом, и «чёрным» фоном кнопок/пилюль
  одновременно (`var(--ink)` + `color:#fff` руками в ~13 местах — mic-button,
  btn-primary, sheet-close, period-pill.active, switch.on и т.д.). В тёмной
  теме `--ink` обязан стать светлым (это текст), но эти кнопки не должны
  вслед за ним стать светлым текстом на светлом фоне — поэтому `--accent`
  (= `--ink` в светлой, но НЕЗАВИСИМО светлый в тёмной) и `--on-accent` (=
  белый в светлой, тёмный в тёмной) заведены отдельно, и все ~13 мест
  переведены на `background: var(--accent); color: var(--on-accent)` вместо
  жёсткого `var(--ink)`/`#fff`. Если добавляется НОВАЯ «чёрная пилюля»
  (primary-кнопка, активная плашка) — всегда через `--accent`/`--on-accent`,
  никогда напрямую `--ink`/`#fff`, иначе в тёмной теме будет светлый текст
  на светлом фоне.
- **Иконки категорий/кошельков инвертируются, а не тускнеют**: в светлой
  теме — бледный `cat.bg` фон + насыщенный `cat.fg` глиф (как раньше,
  значения из `SEED_CATEGORIES`/`SEED_WALLETS` в `db.js` не менялись). В
  тёмной — фон становится САМИМ `cat.fg` (насыщенным), глиф — белым; это
  референс из реального приложения (Qalta), не самопальное решение.
  Механизм — `catIconVars.js` (`{ "--cat-bg": bg, "--cat-fg": fg }`,
  React-инлайн-стиль с CSS custom properties) на каждом из ~18 мест, где
  раньше было `style={{background: X.bg, color: X.fg}}` (`.category-icon`,
  `.wallet-chip-icon`, `.category-pick`, `.insights-card-icon-badge`,
  `.newcat-icon`), + ОДНО общее CSS-правило в `styles.css`, решающее
  `background`/`color` из этих двух переменных по теме. Если добавится
  НОВОЕ место, рисующее цвет категории/кошелька — заводить через
  `catIconVars(bg, fg)`, не напрямую `style={{background, color}}`, иначе
  тёмная тема эту иконку не подхватит (`grep -rn "background:.*\.bg" frontend/src`
  — быстрый способ найти забытые места, тот же приём что и для
  `.emoji`-обхода выше в разделе про иконки).
- **`color-mix()` вместо ручного подбора hex под тёмную тему** — где нужен
  был не сам `cat.fg`/`cat.bg`, а декоративный оттенок (градиент шапки
  Инсайтов, подложка свайпа-удаления, полупрозрачный бэкдроп голосового
  рекордера), использован `color-mix(in srgb, X Y%, var(--surface-или-bg))`
  — автоматически пересчитывается под текущую тему без отдельных
  `[data-theme="dark"]`-веток для каждого случая.
- **Action Button / iOS Shortcuts НЕ могут открыть PWA на конкретном
  экране** — исследовано и заброшено 2026-08-14, НЕ переоткрывать без
  явного запроса пользователя на нативную обёртку. Проверено на реальном
  iPhone пользователя, все три попытки провалились: (1) Add to Home Screen
  игнорирует URL текущей страницы, всегда берёт `start_url` из
  `manifest.json` — второй значок с `?open=wallets` в адресе не помогает;
  (2) даже отдельная статическая страница `/wallets.html` со своим
  `manifest-wallets.json` (`start_url` = сама страница, редирект в
  `?open=wallets` только при `navigator.standalone === true`) технически
  правильно создавала свой значок, но (3) ни «Открыть приложение» в
  Командах (видит только настоящие App Store-приложения, не WebClip), ни
  «Открыть URL-адреса» (всегда открывает Safari, даже при точном совпадении
  URL) не смогли передать управление этому значку. Файлы `wallets.html`/
  `manifest-wallets.json` УДАЛЕНЫ (коммит `b213f1f`) — если тема всплывёт
  снова, единственный реальный путь — обернуть PWA в Capacitor/нативный
  Xcode-проект (пользователь пока не готов на этот объём). Сам механизм
  `?open=wallets` в `App.jsx` (читает `URLSearchParams`, открывает
  `WalletsSheet`, чистит URL через `history.replaceState`) ОСТАВЛЕН — он
  рабочий и безобидный сам по себе, просто не решает Action Button.

## Долги (добавлено 2026-08-15)

Кто должен нам и кому должны мы — личное и семейное, по той же схеме
приватности, что у остальной части приложения. Вход — иконка в шапке
рядом с поиском (`aria-label="Долги"`), она РАНЬШЕ была декоративной
заглушкой «Статистика» (см. «Открытые хвосты» — этот пункт теперь
закрыт, репурпоснута, а не добавлена пятой кнопкой, чтобы не теснить
шапку). Открывает `DebtsSheet.jsx` — полноэкранная страница в стиле
`SettingsSheet`/`RemindersSheet` (свайп вправо закрывает).

- **Две таблицы**: `debts` (`direction` — `owed_to_us`/`we_owe`,
  `user_id` NULL = семейный/shared таким же способом, как
  `wallet_balances`, иначе личный; `amount`/`remaining`, опциональный
  `wallet`, `status` open/closed) и `debt_payments` (по одной строке на
  каждый платёж — `remaining` в `debts` декрементируется явно при
  каждом платеже, не считается через SUM, т.к. платежи, в отличие от
  трат, никогда не редактируются/не удаляются, дрейфа можно не бояться).
- **Опциональная привязка к счёту** (`backend/src/routes/debts.js`) —
  причина, по которой это не отдельная изолированная фича: пользователь
  сам поднял вопрос «если долг вернут на Kaspi, баланс на сайте
  разъедется с реальным счётом». Решение — выдача и погашение долга
  МОГУТ (не обязаны) двигать баланс конкретного кошелька тем же
  анкорным механизмом, что и перевод между кошельками
  (`services/balanceHistory.js` — `getCurrentBalance`/`setBalance`/
  `logBalanceChange`, общие хелперы с `walletBalances.js` и
  `walletTransfers.js`), в ОДНОЙ транзакции с самим долгом/платежом, с
  записью в `balance_history` (`reason`: `debt_lend`/`debt_borrow`/
  `debt_repay_in`/`debt_repay_out`/`debt_delete`). Если счёт не указан
  («Без счёта» — для наличных или долгов, которые сознательно не должны
  трогать баланс) — просто ничего на балансе не меняется.
  Направление движения баланса: `owed_to_us` (мы одолжили) — при
  создании баланс УМЕНЬШАЕТСЯ (деньги ушли), при погашении
  УВЕЛИЧИВАЕТСЯ (деньги вернулись); `we_owe` (нам одолжили) — наоборот.
- **Удаление долга** разрешено ТОЛЬКО пока `remaining === amount` (ни
  одного платежа ещё не было) — реверсит привязку к балансу, если она
  была, и удаляет строку. Как только появился хотя бы один платёж,
  удалить нельзя — только продолжать гасить (иначе пришлось бы
  откатывать историю баланса по каждому отдельному платежу, что не
  вошло в объём v1, если понадобится позже — см. `debtsRouter.delete`
  в `routes/debts.js`, там это explicitly задокументировано как
  осознанное ограничение, не забытый кейс).
  Симметрично, «Погасить» не даёт ввести сумму больше `remaining` —
  бэкенд и фронтенд оба это проверяют.
  «Погасить полностью» в `DebtDetailSheet.jsx` — кнопка-подсказка,
  просто префиллит инпут суммой остатка, ничего не отправляет сама.
- **Видимость** — как у всего остального с этим же shared/private
  сплитом: `GET /api/debts`/`GET /api/debts/:id/payments` отдают строки,
  где `user_id IS NULL OR user_id = req.user.id`; кто из двух аккаунтов
  сделал платёж — `changed_by`/`changed_by_name` в ответе (важно на
  семейных долгах, чтобы было видно, кто гасил).
- **Даты** (добавлено тем же вечером, по запросу): `debts.due_date`
  (nullable DATE, `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` — та же
  идемпотентная миграция, что у `users.theme`/`wallets.shared`, т.к.
  таблица `debts` к этому моменту уже жила на проде с реальными
  данными). Опциональный `type="date"` инпут в `NewDebtSheet.jsx`
  (тот же `.period-picker-field` стиль, что у кастомного диапазона
  периода). `DebtDetailSheet.jsx` показывает и «Дата выдачи»
  (`created_at`, уже была в БД, просто не выводилась), и «Дата
  погашения» (`due_date` или «Не указана»).
- **Погашение — без выбора счёта** (пофикшено тем же вечером): раньше
  форма погашения давала выбрать ЛЮБОЙ счёт заново, что могло увести
  баланс не туда, куда деньги реально пришли. Теперь `POST
  /api/debts/:id/payments` больше не принимает `wallet` от клиента —
  всегда берёт `debt.wallet` (счёт, зафиксированный при создании долга)
  сам на бэкенде. `DebtDetailSheet.jsx` вместо пикера показывает строку
  «Сумма зачислится/спишется с баланса «X»».
- **`.categories-sheet` обрезал контент выше 92vh** (реальный баг,
  найден на разросшемся списке платежей в `DebtDetailSheet` — терялась
  строка «Комментарий»): контейнер — flex-column с ФИКСИРОВАННОЙ
  высотой `92vh` и `overflow-y:auto`, но у детей по умолчанию
  `flex-shrink:1` — когда контента становилось больше 92vh, flexbox
  СЖИМАЛ дочерние блоки вместо того, чтобы отдать это на откуп
  `overflow-y`, а `.settings-group` (`overflow:hidden`) обрезал то, что
  не влезло. Фикс — `.categories-sheet > * { flex-shrink: 0; }`,
  касается ВСЕХ шторок на этом классе (`CategoriesSheet`,
  `NewWalletSheet`, `WalletTransferSheet` и т.д.), не только долгов —
  просто раньше ни у одной не было настолько длинного контента, чтобы
  проявиться.
- **Сырые reason-коды из `balance_history` протекали в UI**: у
  `debt_lend`/`debt_borrow`/`debt_repay_in`/`debt_repay_out`/
  `debt_delete` не было записи в `REASON_LABEL`
  (`BalanceHistorySheet.jsx`), поэтому показывался код как есть — та же
  дыра, что уже чинили для `transfer_in`/`transfer_out`, просто не
  продублировали для долгов. Добавлены подписи + имя контрагента через
  `counterpart_wallet` (переиспользуется под имя человека, не счёта, для
  строк долгов — см. комментарий в `logBalanceChange`-вызовах
  `routes/debts.js`). На будущее — фолбэк на де-snake_case вместо сырого
  кода, если для нового `reason` забудут добавить подпись.
- Спроектировано и задеплоено за один проход по явному разрешению
  пользователя ночью («не спрашивай ни о чём, делай и сразу пуш») — см.
  [[dariya-workflow]]. Проверено локальным изолированным браузер-тестом
  с замоканным `fetch` (создание с привязкой к счёту, полное погашение,
  видимость кнопки удаления до/после платежа, фильтр
  «Мне должны»/«Я должен», подсчёт «Открыто»), реальной Postgres под
  рукой не было — если что-то не так именно на проде (не в UI-логике, а
  в самих SQL-запросах/транзакциях), это первое, что стоит перепроверить.

**Обновлено 2026-08-16** (два запроса пользователя, оба про изоляцию
между аккаунтами — см. «Баланс: полный переход на per-account» ниже

- **Погасить/удалить долг может ТОЛЬКО создатель** (`debt.created_by`),

  `getCurrentBalance`/`setBalance` из `balanceHistory.js`, но БЕЗ
  параметра `shared` (убран целиком, см. ниже).

## Капитал (добавлено 2026-08-16)

Семейный капитал (активы минус обязательства), который пользователи
раньше считали вручную в отдельном Excel-файле раз в месяц-два — теперь
своя страница. Вход — иконка в шапке рядом с настройками
(`aria-label="Капитал"`), которая РАНЬШЕ была декоративной заглушкой
«Кошельки»(cylinder) — см. «Открытые хвосты» п.3, теперь закрыт,
репурпоснута так же, как раньше «Статистика» → «Долги».

- **Схема, две таблицы**: `capital_snapshots` (`id`, `created_by`,
  `created_at`) и `capital_items` (`snapshot_id`, `kind` — `asset`/
  `liability`, `name`, `amount`, `sort_order`). **Семейное по дизайну,
  БЕЗ `user_id`-скоупа** — в отличие от долгов, оба аккаунта видят и
  могут редактировать/удалять ЛЮБОЙ снимок, не только свой — так и было
  задумано (это общая цифра семьи, не персональная). Итого/прирост
  НИГДЕ не хранятся — всегда живой `SUM` по `capital_items` (тот же
  принцип, что `wallet_balances`/`debts.remaining` для тех вещей, где
  это оправдано отсутствием риска дрейфа).
- **Роуты** (`backend/src/routes/capital.js`): `GET /` (список с
  computed `total`/`assets_total`/`liabilities_total`), `GET /:id`
  (разбор по позициям), `POST /` (создание, опциональный `createdAt`
  для бэкфилла задним числом — см. ниже), `PUT /:id` (редактирование —
  **wholesale replace**, не diff: `DELETE FROM capital_items WHERE
  snapshot_id = $1` + заново `INSERT` всех строк, тот же подход, что

## Баланс: полный переход на per-account (добавлено 2026-08-16)

**Реальный прод-баг, найденный пользователем**: «Баланс» на общем
кошельке (Семья/Бизнес/Ремонт) был ОДНОЙ строкой в `wallet_balances`
(`user_id IS NULL`, "shared row") на ДВА аккаунта — значит: (1) трата
ЛЮБОГО из двух аккаунтов вычиталась из ОБЩЕГО баланса, который видели
ОБА, а не только траты того, кто смотрит; (2) кто последний скорректировал
цифру («Баланс» → тап → новое число), тот и был «источником правды» для
ОБОИХ — Дария физически видела число, которое последним вбил Есенжан.
Подтверждено эмпирически через `balance_history` до фикса (нашли запись
`changed_by: 2` — Дария просто открыла «Баланс», ничего не меняя, и это
перезаписало `base_at` на строке, которую видел и Есенжан).

**Фикс — три слоя, все нужны вместе**:
1. **Схема** (`db.js`): убран `wallet_balances_shared_uidx` (партиальный
   уникальный индекс на `(wallet) WHERE user_id IS NULL`), оставлен
   только `wallet_balances_private_uidx` на `(wallet, user_id)`. Миграция
   (идемпотентный `DO $$ ... $$` блок, безопасно гонять на каждом
   деплое) находит все оставшиеся `user_id IS NULL` строки и клонирует их
   по одной на каждого реального пользователя из `users`, с ОДИНАКОВЫМ
   `base_amount`/`base_at` — оба аккаунта стартуют с той же цифры, дальше
   расходятся независимо по своим же тратам. **Это разовая миграция
   истории** — после неё цифра баланса на общих кошельках у пользователя,
   который меньше тратил с последней коррекции, ЗАМЕТНО подскочит вверх
   (раньше туда вычитались чужие траты тоже) — это ожидаемо, не баг, если
   пользователь спросит «откуда взялись деньги».
2. **`services/balanceHistory.js`**: `getCurrentBalance`/`setBalance`
   потеряли параметр `shared` целиком — теперь ВСЕГДА работают по
   `(wallet, user_id)`, без ветки на общий кошелёк. `isSharedWallet`
   (было экспортировано отсюда) удалено как мёртвый код — использовалось
   только для этого параметра.
3. **Все вызывающие места** обновлены синхронно (иначе опять «фикс в
   одном месте, не продублирован» — см. урок в [[expense-web-project]]):
   `routes/walletBalances.js` (GET и PUT), `routes/debts.js` (создание/
   погашение/удаление с привязкой к счёту), `routes/walletTransfers.js`
   (обе ноги перевода). **`routes/balanceHistory.js`** (эндпоинт «История
   балансов») тоже переведён на строгую фильтрацию `bh.changed_by = $1`
   вместо `w.shared OR bh.changed_by = $1` — на общих кошельках теперь
   каждый видит только СВОИ собственные записи истории, не записи
   партнёра.

**Что осталось НЕ тронутым специально**: видимость самих трат
(`expenses`) на общих кошельках — это отдельная, уже давно работающая
пуловая модель (оба видят все траты друг друга в списке/Инсайтах,
кроме тумблера «Только мои»), её никто не просил менять, речь только
про ЧИСЛО баланса. Долги/переводы остаются механизмом «явно двигаю
чей-то баланс», просто теперь скоуп — тот, кто нажал кнопку, а не
общий anchor.

### Трата задним числом не уменьшала баланс (найдено и починено 2026-08-29)

Симптом: добавили расход, вручную поставив вчерашнюю дату — «Расходы»
выросли, а «Баланс» не сдвинулся. Без правки даты всё работало.
Воспроизведено на ВСЕХ четырёх кошельках, «Бизнес» тут ни при чём —
просто у него якорь баланса был свежее всех.

Причина: баланс — это якорь (`base_amount` на момент `base_at`) минус
траты, и отрез шёл по `created_at > base_at`. Но `created_at` — это дата,
КОГДА потратили, и её свободно правит шторка редактирования. Трата,
внесённая сегодня, но датированная вчера, оказывается ДО якоря,
выставленного сегодня утром, и в вычитание не попадает. Зеркальный баг:
правка даты старой траты на «раньше якоря» молча возвращала деньги.

Починка: колонка `expenses.logged_at` — момент, когда строка была
ЗАПИСАНА (`DEFAULT now()`, никем не переопределяется, правка даты её не
трогает), и отрез теперь по ней. Копий этого SQL ровно две —
`routes/walletBalances.js` (GET) и `services/balanceHistory.js`
(`getCurrentBalance`, через него ходят переводы и долги); держать
одинаковыми.

**Миграция намеренно консервативная**: `logged_at` бэкфилится из
`created_at`, а не дефолтится в `now()`. Иначе все прошлые траты стали бы
«записанными в момент деплоя», то есть после любого существующего якоря,
и все балансы в приложении рухнули бы на всю историю трат. Побочный
эффект бэкфилла: траты, внесённые задним числом ДО этого деплоя, так и
останутся невычтенными — если такие есть, баланс правится руками.

### Список трат обрезался по-разному в разных кошельках (починено 2026-08-29)

Симптом: на «Все счета» список кончался 20 августа, а внутри «Семьи» шёл
с 1-го. Причина — `refreshAll` просил у бэкенда **последние 50 строк без
дат** (`limit: 50`). Насколько далеко назад дотягивались эти 50, зависело
от плотности выборки: на «Все счета» они размазываются по всем кошелькам
И обоим аккаунтам (общие кошельки видны обоим), поэтому упирались в
середину месяца, а в одном кошельке покрывали весь. Обрезание было
молчаливым — никакой пометки, что список неполный.

Починка: список запрашивается по границам выбранного периода
(`periodRange`), теми же, что уже используют сводка сверху и Insights;
`limit` остался только предохранителем (2000, как в
`fetchExpensesRange`). Теперь список показывает ровно тот период, который
подписан в шапке, и не зависит от выбора кошелька.

**Побочный эффект, принят намеренно:** период «Сегодня» теперь и список
сокращает до сегодняшних трат (раньше там висели последние 50 за любые
дни). Это то же правило, по которому уже живут «Расходы за» и Insights.

## Дублирование трат — два РАЗНЫХ бага, оба найдены и починены 2026-08-16

Пользователь дважды сообщал «трата задвоилась» с разницей в несколько
часов — это оказались два независимых бага, не один и тот же:

1. **Визуальный дубль на несколько секунд** (первый репорт): офлайн-
   очередь после успешного `POST` держит запись в `syncedShadow`
   (`offlineQueue.js`) до подтверждающего `refreshAll`, чтобы не мигало
   «исчезла-появилась». `clearConfirmedSynced(fetchStartedAt)` сравнивал
   МОМЕНТ ОТПРАВКИ запроса, а не момент его реального прихода на сервер —
   на холодном старте Render (или упёршись в лимит браузера на
   одновременные соединения к одному origin) более РАННИЙ по времени
   отправки `refreshAll` мог реально долететь ПОЗЖЕ и уже содержать
   свежую трату, но shadow-запись это не считывало и не убирало.
   Фикс — `mergeAndSet` (`App.jsx`) теперь ВСЕГДА дедуплицирует по `id`
   при слиянии `pendingForList`/shadow с только что зафетченными
   строками, независимо от таймингов — затрагивает список трат, суммы по
   кошелькам и Инсайты разом (все три места брали разные пересечения тех
   же массивов).
2. **Настоящий дубль — вторая строка в БД** (второй репорт, серьёзнее):
   офлайн-очередь ретраит `createExpense`, если не может отличить
   «запрос вообще не дошёл» от «дошёл, сервер сохранил, но ответ
   потерялся» (оба варианта — просто `catch` и запись остаётся в
   очереди) — на холодном старте Render это реально происходило, и
   повтор создавал ВТОРУЮ настоящую строку с другим `id`. Фикс —
   `idempotency_key` в `expenses` (новая колонка + частичный уникальный
   индекс `(user_id, idempotency_key) WHERE idempotency_key IS NOT NULL`):
   `enqueueExpense`'s `localId` (уже был уникальным) теперь едет на сервер
   как ключ, `POST /api/expenses` делает `ON CONFLICT ... DO NOTHING` и
   при конфликте отдаёт УЖЕ СУЩЕСТВУЮЩУЮ строку вместо новой. Голос/скан/
   бэкфилл не задействованы (не шлют ключ, `NULL` никогда не конфликтует
   сам с собой).

  за период. Тап по цифре — инлайн-редактирование (только когда выбран
  конкретный счёт; на «Все счета» строка read-only, показывает сумму по
  всем счетам, у которых баланс вообще задан). **Сохранение только явное**
  (2026-08-29): под полем появляются «Отмена» и «Сохранить», причём
  «Сохранить» активна лишь когда число реально изменилось, и первый тап по
  ней взводит подтверждение («Точно сохранить?»), а пишет только второй.
  Раньше висело на `onBlur` — любой тап мимо поля молча перевыставлял
  якорь; именно так в истории и появилась запись `changed_by: 2` от
  простого открытия строки (см. «Баланс: полный переход на per-account»).
  Enter теперь только убирает клавиатуру и ничего не сохраняет. Хранится НЕ как бегущий
  счётчик, который надо было бы декрементить в каждом месте, где трата
  создаётся/правится/удаляется/приходит офлайн-очередью/пишется ботом
  напрямую в Postgres — а как якорь (`base_amount` на момент `base_at`).
  Текущий баланс = `base_amount − SUM(трат этого счёта с logged_at >
  base_at)` (именно `logged_at` — момент записи строки, не дата траты; см.
  «Трата задним числом не уменьшала баланс» выше), считается на бэкенде
  при каждом `GET /api/wallet-balances`
  (`routes/walletBalances.js`) — всегда консистентен независимо от того,
  как трата попала в БД. Тот же shared/private сплит, что у
  `category_limits` (см. «Лимиты по категориям» выше): одна общая строка на
  Семья/Бизнес/Ремонт, своя строка на аккаунт у Личные. Новая таблица
  `wallet_balances`. **Фикс того же дня**: удаление траты выглядело так,
  будто баланс «не восстанавливается» — на сервере он и так был верным
  сразу (SUM живой, удалённая строка просто больше не считается), но
  фронт показывал старое число до 4 секунд (окно отмены удаления) плюс
  сетевой раунд-трип, потому что баланс брался только из последнего
  `fetchWalletBalances()`, а не из той же оптимистичной подмены, что уже
  применяется к `walletTotals` в `mergeAndSet`. Теперь `App.jsx` держит
  `pendingWalletDeltas` (тот же `pendingByWallet`, что `mergeAndSet` уже
  считает для `walletTotals`) и вычитает его из баланса: при добавлении
  офлайн-траты (дельта положительная) баланс падает сразу, при удалении

  - Синхронизация очереди: НЕ полагается только на событие `online` или
    `visibilitychange` — на iOS Safari (особенно standalone PWA) они
    ненадёжны. App.jsx дополнительно ПОЛЛИТ каждые 15с, пока в очереди
    что-то есть. Эти 4 триггера (mount/`online`/`visibilitychange`/poll)
    раньше могли сработать одновременно и оба прочитать один и тот же
    снэпшот очереди — при медленном холодном старте Render это дважды
    отправляло одну и ту же офлайн-трату. Починено 2026-08-13: модульный
    флаг `syncing` в `offlineQueue.js` (не React-state — переживает разные
    вызовы `syncPendingExpenses` как единый мьютекс), повторный вызов пока
    первый ещё летит — no-op.
  - Несинхронизированная (`pending`) трата хранит `created_at` момента
    добавления и раньше безусловно попадала в ЛЮБОЙ период — с «месяцем»
    как единственным периодом это почти не было заметно, но с «Сегодня»/
    кастомным диапазоном (см. выше) старая незасинканная трата могла
    накручивать «сегодняшний» итог. Починено тем же днём: `mergeAndSet`
    фильтрует pending-траты по `periodRange(currentPeriod)`, как и
    серверные строки.
  - Инсайты и главный экран — см. выше, полностью локальная арифметика.

## Захардкоженные знания о платформе (не переоткрывать!)

- **Вибрация на iOS Safari**: Vibration API нет. Хак — программный клик по
  label скрытого `<input type="checkbox" switch>` (`haptics.js`). Из НАСТОЯЩИХ
  click-обработчиков работает надёжно (iOS 17.4–26.4). Из touch-обработчиков
  (карусель-тик при скролле) — попытка есть, но по опыту iOS такое обычно
  блокирует; не гарантировано, могло не сработать на текущей версии iOS
  пользователя — не удивляться отсутствию вибрации на скролле.
  setTimeout-отложенный клик убивает даже рабочие случаи (только
  `hapticHeavy` — двойной клик — использует один отложенный на 120мс, это
  ещё держится). На Android — navigator.vibrate везде, надёжно.
- **iOS PWA восстанавливается из памяти** без перезагрузки — пользователь
  может видеть старую версию, пока не убьёт приложение из переключателя.
  Для смены ИКОНКИ на экране Домой этого НЕДОСТАТОЧНО — iOS кэширует иконку
  с момента добавления, нужно удалить с экрана Домой и добавить заново.
- **iOS PWA переспрашивает разрешение на микрофон/камеру при каждом
  полном закрытии** (жалоба пользователя 2026-08-16) — разрешение
  хранит браузер/ОС, у сайта НЕТ API это изменить, это НЕ то, что можно
  починить кодом. Известное поведение WebKit конкретно для standalone
  home-screen PWA (в отличие от обычной вкладки Safari, где разрешение
  обычно держится). Единственное, что реально сделали — добавили
  `id`/`scope` в `manifest.json` (их не было, по спеке правильно иметь) —
  это НЕ подтверждённый фикс, просто гигиена, которую в паре сторонних
  отчётов связывают с похожими проблемами консистентности установленного
  PWA. Реальный рычаг у пользователя — Настройки → Safari → Камера/
  Микрофон на самом iPhone, не что-либо в этом репо. Не переоткрывать
  как «баг сайта», если пользователь снова пожалуется — проверить,
  помогло что-то из этого или нет, прежде чем предполагать.
- **Deepgram**: финализирует фразу только по ≥500мс тишины В ПОТОКЕ или по
  CloseStream. Обрыв аудио без стоп-маркера = вечное «Обрабатываю…».
  Аудио, пришедшее до открытия сокета (клиентского или серверного к DG),
  раньше молча ДРОПАЛОСЬ — терялся заголовок контейнера и весь поток
  становился непарсибельным. Теперь буферизуется с обеих сторон.
- **Service worker**: HTML-шелл И хэшированные ассеты — ОБА
  stale-while-revalidate, единым обработчиком (пофикшено 2026-08-14 — жалоба
  «онлайн белый экран при загрузке, офлайн открывается мгновенно»). Раньше
  HTML был network-first («чтобы редеплой не залипал на старой версии») —
  на практике это значило, что ОНЛАЙН открытие всегда ждало реальный
  раунд-трип до показа чего-либо, а ОФЛАЙН — мгновенный фейл фетча и
  мгновенный фоллбэк на кэш, то есть офлайн субъективно казался БЫСТРЕЕ.
  Ничего в `sw.js` не чистит старый закэшированный ассет, когда приходит
  новый (`CACHE_NAME` меняется, и старые записи подчищаются в `activate`,
  только когда меняются БАЙТЫ самого `sw.js` — обычный деплой фронта его не
  трогает), так что закэшированный старый HTML безопасно ссылается на свои
  же ещё закэшированные хэшированные ассеты — упасть в 404 неоткуда. Теперь
  ОБА типа запросов идут через один и тот же обработчик: мгновенный пейнт
  из кэша, если он есть, фоновый фетч освежает кэш к следующему разу. Минус
  — свежий деплой может показаться не с первого открытия, а со второго
  (фон уже подтянул новую версию к тому моменту). Подтверждено через
  Navigation Timing API: `deliveryType: "cache-storage"`, `transferSize: 0`.
  Ловушка при клонировании Response: `.clone()`
  обязан случиться в САМОЙ ПЕРВОЙ реакции на `fetch()`, до того как
  потребитель `respondWith` (браузер, рендерящий навигацию) начнёт читать
  тело — иначе гонка и «body is already used», кэш молча не пишется.
- **Vercel**: аккаунт залогинен в CLI (`esenzhan`). Проект **`expense-web`**
  на Vercel настроен с **Root Directory = `frontend`** — значит
  `npx vercel deploy --prod --yes` нужно запускать из КОРНЯ репозитория, НЕ
  из `frontend/` (запуск изнутри `frontend/` даёт ошибку
  «Root Directory "frontend" does not exist», т.к. Vercel тогда ищёт
  `frontend/frontend`). И корневой `.vercel/project.json`, и
  `frontend/.vercel/project.json` указывают на один и тот же
  `projectId`/`expense-web` — привязка не потеряна, дело только в том, откуда
  запускать команду. ОПАСНОСТЬ: обычный `npx vercel deploy` без явной
  привязки может создать/задеплоить в НОВЫЙ проект (однажды случайно возник
  лишний проект «frontend» в том же scope) — если `vercel ls` показывает не
  тот проект, перелинковать `npx vercel link --yes --scope tommili1
  --project expense-web`. Частый curl на прод-домен ловит Vercel Security
  Checkpoint (антибот) — проверять через браузер/browser-пейн, не
  curl-полингом самой HTML-страницы (статические ассеты типа
  `/icon-512.png` curl'ить можно).
- **Render free tier**: холодный старт 30–50с (иногда дольше) — все
  таймауты/буферы (WS-реконнект, fallback-таймеры голоса) это учитывают.
  Фронт шлёт fire-and-forget GET `/api/health` при открытии приложения и по
  возврату в форграунд, чтобы будить сервер заранее.
- **Деплой теперь ПОЛНОСТЬЮ автоматический через один `git push`**: Vercel
  подключён к GitHub и передеплоивает фронт на пуш в `main` сам по себе —
  ручной `npx vercel deploy --prod --yes` из корня репо, который раньше был
  обязательным шагом, БОЛЬШЕ НЕ НУЖЕН (Render и так уже автодеплоил бэкенд).
  Проверять фактически раздаваемый бандл всё равно нужно (см. «Как
  тестировать» ниже) — Vercel-деплой занимает ~10–40с после пуша.
  **Наблюдение 2026-08-16 (Claude Code сессия, не факт про самого
  пользователя)**: с конкретно этой sandbox-сети (edge-нода `hkg1` в
  заголовках) `curl`/фетч на прод-домен НЕОДНОКРАТНО отдавал `x-vercel-
  cache: HIT` со СТАРЫМ бандлом от 5 до ~20 минут после того, как `npx
  vercel inspect` уже показывал новый деплой как `Ready`/`Production` —
  это не то же самое, что Security Checkpoint из пункта выше (там просто
  антибот-страница, тут реальный старый JS с кодом 200). Не факт, что
  реальный пользователь на СВОЁМ телефоне видит ту же задержку — его
  собственные проверки в этой же сессии заметно опережали то, что видел
  Claude Code с этой sandbox-сети. Если нужно быстро подтвердить, что
  деплой реально живой, не дожидаясь пользователя — надёжнее дёрнуть сам
  бэкенд-эндпоинт (Render, отдельная инфраструктура, такой проблемы не
  наблюдалось) через авторизованный `fetch` из уже залогиненной
  браузер-вкладки, чем полагаться на посвежевший фронтенд-бандл.
- **Флекс-контейнер, который сам скроллится (`overflow-x/y: auto`),
  ВНУТРИ другого флекс-контейнера с ФИКСИРОВАННОЙ высотой** (например,
  `height: 92vh`): по спецификации его «автоматический минимальный
  размер» по поперечной оси считается НУЛЁМ, а не по контенту — если
  соседям по общей колонке не хватает места, `flex-shrink` схлопывает
  именно такой элемент в его же паддинг, а не пропорционально всем.
  Дважды ловили на этом (`.wallet-tabs`, затем `.newcat-suggestions`/
  `.palette-row`) — лечится явным `min-height` на самом скроллящемся
  элементе, полагаться на высоту контента внутри нельзя.
  `.wallet-tabs` в итоге вообще переведён на `flex-wrap: wrap` вместо
  скролла — так безопаснее и последовательнее с остальным UI
  (`.period-toggle` уже так делал).
- **`InsightsButton`** слушает `touchstart/move/end` на `document`
  ЦЕЛИКОМ (чтобы тянуть шторку вниз можно было с любого места главного
  экрана), с исключающим списком селекторов (`.sheet-backdrop`,
  `.recorder-dock` и т.п.), которые не должны участвовать в этом жесте.
  Любая НОВАЯ область со своим тач-жестом (например `.expense-row-wrap`
  для свайпа-удаления) должна попасть в этот список, иначе оба
  распознавателя жеста дерутся за один и тот же touch при малейшем
  вертикальном дрожании пальца во время горизонтального свайпа.
- **iOS Safari не чистит Cache Storage/service worker при удалении
  PWA-иконки с экрана Домой и повторном добавлении** — они привязаны к
  origin, а не к иконке, старый бандл может продолжать раздаваться. Для
  реального сброса — Настройки → Safari → Дополнительно → Данные сайтов
  → удалить для домена (или сначала проверить в приватной вкладке Safari,
  что дело именно в кэше, а не в реальном баге).
- **`initSchema()` (`db.js`) выполняется на КАЖДОМ старте бэкенда, а не
  один раз** — значит любой безусловный seed-луп (`INSERT ... ON CONFLICT
  DO NOTHING`) тихо ВОСКРЕШАЕТ то, что пользователь намеренно удалил,
  на каждом деплое/рестарте, потому что `DO NOTHING` отличает только
  дубликат от новой строки, а не «никогда не было» от «удалено». Ловили
  дважды (2026-08-13): сначала на категориях (реальный прод-инцидент —
  пользователь почистил категории по кошелькам, следующий деплой всё
  вернул обратно), потом на кошельках нашли ровно тот же паттерн при code
  review и починили превентивно. Фикс — оборачивать сид в `SELECT 1 FROM
  <table> LIMIT 1`, сеять только если таблица ПУСТА (реально первый
  запуск), не на каждом боте. Если добавляется новая таблица с
  дефолтными строками — сразу проверять этот паттерн, не ждать инцидента.
- **Браузер-пейн: скриншот НЕ всегда 1:1 с реальным viewport** — координаты
  из `computer{action:"screenshot"}` иногда были в 2–2.5 раза «крупнее»
  фактического CSS-пиксельного пространства (наблюдалось при некоторых
  viewport/масштабах в этой сессии), из-за чего клики по сырым
  координатам мимо промахивались (например пилюля «Сегодня» или строка в
  списке кошельков). Симптом — клик визуально «не сработал», хотя элемент
  на скриншоте на месте. Надёжный путь — `read_page` → клик по `ref`, а не
  по вычисленным из скриншота координатам; сверять `Viewport: WxH` в
  выводе `read_page` со размером скриншота, если координатный клик не
  сработал. В этой же сессии `computer{action:"left_click"}` иногда просто
  таймаутился (30с) без видимой причины на статичной странице — рабочий
  обход: клик тем же элементом через `javascript_tool` →
  `el.click()`/`dispatchEvent`, не переигрывать `computer` в цикле.
- **Фон под шторкой (`.sheet-backdrop`) может скроллиться при свайпе ВВЕРХ
  по короткой шторке** (`.categories-sheet`, `height: 92vh`,
  `overflow-y: auto`, но контента может быть меньше — например «Счета»/
  «Новый счёт», 4-5 строк) — нашли и починили 2026-08-13. `useSwipeDismiss`
  (`sheetGestures.js`) ловит только жест ВНИЗ (закрытие) и специально
  «отпускает» (не вызывает `preventDefault`) любой другой жест — расчёт был
  на то, что вверх/скролл поймает СОБСТВЕННЫЙ `overflow-y:auto` шторки. Но
  если контент короче контейнера, скроллить внутри нечего, а не
  предотвращённый `touchmove` на позиционированном `fixed` бэкдропе всё
  равно даёт iOS повод прокрутить ближайшего скроллящегося предка — список
  ПОЗАДИ шторки (классический scroll-chaining через `position:fixed`,
  описанный в шапке `sheetGestures.js`, но раньше не для ЭТОГО случая).
  Фикс — `preventDefault` теперь вызывается и на upward-свайпе, но ТОЛЬКО
  если `el.scrollHeight <= el.clientHeight` (действительно нечего
  скроллить) — длинные шторки (Категории, Настройки) не тронуты, у них
  внутренний скролл как и был. Если где-то ещё появится короткая шторка на
  классе `.categories-sheet`/`useSwipeDismiss` — этот фикс уже общий,
  ничего добавлять не нужно.
- **`WalletsSheet` остаётся смонтированной, пока открыт `NewWalletSheet`
  поверх неё** (тап «+» внутри «Счета» НЕ закрывает список счетов,
  `walletsOpen` не сбрасывается) — то же самое для Категорий
  (`categoriesOpen`/`newCategoryWallet`). Это НАМЕРЕННЫЙ паттерн (шторка на
  шторке), не баг — закрытие верхней шторки естественно возвращает к
  списку под ней. Не «чинить» унификацией стейта при следующей уборке.

## Как тестировать без телефона

- Синтез русской речи: `say -v Milena -o x.aiff "текст"` + `afconvert -f WAVE
  -d LEI16@16000 -c 1`. Честный тест голосового потока — страница в
  браузер-пейне, WAV → WebAudio → MediaStreamDestination →
  MediaRecorder(webm/opus) → прод-WS (скрипт эфемерный, пересоздавать по
  надобности).
- Жесты/скролл в браузер-пейне: синтетические TouchEvent/Touch или прямые
  DOM-манипуляции (`scrollTo`, dispatch `MouseEvent` на кнопки) — реального
  тач-скролла эмулятор не даёт, но для проверки логики (не плавности)
  достаточно.
- **`element.blur()` в браузер-пейне НЕ фокусирован по-настоящему** —
  native `.blur()`/`.focus()` не генерируют реальные `blur`/`focusout`
  события (проверено 2026-08-14 на тесте `AccountBalanceRow`'s onBlur-save:
  `document.activeElement` после `.focus()` показывал нужный элемент, но
  ни один `blur`/`focusout`-listener не срабатывал, даже на capture-фазе
  `document`). Рабочий обход — диспатчить `FocusEvent` вручную:
  `el.dispatchEvent(new FocusEvent('blur')); el.dispatchEvent(new
  FocusEvent('focusout', {bubbles: true}))`. React слушает делегированно
  через `focusout` (не `blur`, он не всплывает), так что именно это и нужно
  подделать, `.blur()` тут бесполезен.
- **Частичный `window.fetch`-мок валит ВСЕ данные, не только немокнутый
  запрос** — если код делает `Promise.all([...])` (как `refreshAll` в
  `App.jsx`: expenses/stats/expenses-range/wallet-balances разом), а
  замокан только ОДИН из них, остальные бьются об реальную сеть и падают
  (`ERR_CONNECTION_REFUSED` в дев-окружении без бэкенда) — весь `Promise.all`
  реджектится, и даже успешно замоканные данные никогда не применяются.
  Мокать нужно ВСЕ URL, которые дёргает конкретный флоу, не только тот,
  что проверяешь.
- Офлайн — НЕ полагаться на devtools-подобный офлайн-тумблер (browser-пейн
  его не даёт); эмулировать патчем `window.fetch`, что для сетевых запросов
  на прод-домен кидает reject — но это НЕ проверяет service-worker'ный
  network-layer (SW живёт в отдельном контексте, page-level monkeypatch его
  не трогает) — для проверки самого офлайн-шелла (SW) нужен реальный
  офлайн/самолётный режим на телефоне.
- Кадры из видео-референсов: swift-скрипт с `AVAssetImageGenerator`
  (эфемерный, в `scratchpad/` текущей сессии — пересоздавать по надобности).
  Для покадрового разбора конкретных моментов — вырезать частоту кадров
  повыше (30fps) в узком временном окне, а не весь ролик через 10fps.
- В браузер-пейне таймеры/анимации троттлятся — замеры «через N мс» врут,
  доверять итоговому состоянию DOM/computed style, не таймингу.
- После любого прод-деплоя (просто `git push`, см. хардкод про Vercel
  autodeploy) — дождаться, что фактически отдаваемый бандл (`curl` на
  `/`, вытащить хэш `<script src>`) сменился по сравнению с тем, что было
  до пуша, прежде чем тестировать — Vercel-деплой занимает ~10–40с, а
  вручную открытый браузер-пейн может показать старый HTML ещё пару
  секунд после этого.
- Для проверки НОВОГО React-компонента (особенно визуально/CSS) без
  логина и без прохождения всего приложения — временный отдельный
  vite-энтрипоинт: `frontend/test-X.html` + `frontend/src/test-X-main.jsx`
  (обычный `ReactDOM.createRoot(...).render(<Компонент ... />)` с
  моковыми пропсами), открыть в браузер-пейне на `localhost:5173/test-X.html`
  через `preview_start`. Для компонентов, которые сами дёргают API
  (категории/лимиты, поиск и т.п.) — в том же test-X-main.jsx подменить
  `window.fetch` на обёртку, которая матчит нужный URL и отдаёт
  моковый `Response`, остальное пробрасывать в оригинальный `fetch` —
  не нужен ни логин, ни реальный бэкенд, а дебаунс/гонки/race-guard
  проверяются по-настоящему (так ловили баг с двойной отправкой офлайн-
  очереди и проверяли дебаунс поиска). Обязательно удалить оба файла и
  проверить `git status`, прежде чем коммитить — они не для репозитория.
  Так же можно быстро вывести на экран одиночный SVG-глиф в реальном размере
  (150px+) через `javascript_tool` → `document.body.innerHTML = '<svg ...>'`
- **Service worker на `localhost:5173` переживает между тестами и ломает
  их** (нашли 2026-08-15): `main.jsx` регистрирует `/sw.js` безусловно,
  даже в dev — если браузер-пейн хоть раз открывал `localhost:5173`
  раньше в ЭТОЙ сессии (или вообще когда-либо в этом профиле), SW уже
  активен для origin и перехватывает КАЖДЫЙ последующий GET, включая
  свежесозданный `test-X.jsx` — в лучшем случае отдаёт устаревший кэш, в
  худшем (замечено на новом файле, которого раньше не существовало) браузер
  ругается на неверный MIME-тип модуля, хотя `curl` на тот же URL
  показывает корректный ответ от самого vite. Перед любым тестом через
  `test-X.html` — сначала `navigator.serviceWorker.getRegistrations()` →
  `.unregister()` на все + `caches.keys()` → `caches.delete()` на все,
  ПОТОМ `navigate`. Надёжнее всего — новый `tabs_create`, а не переиспользовать
  вкладку, где уже открывался прод/дев на этом origin.
  — не полагаться на маленький thumbnail в общей галерее иконок, там
  форма/баги не видны (см. «Категории per-wallet» про иконку скутера).
- Массовая загрузка исторических данных (бэкфилл трат с реальными датами)
  — НЕ через прямой доступ к БД (обычно недоступен локально) и не через
  `X-Bot-Key` (в этой сессии его не было под рукой). Рабочий путь: открыть
  прод-сайт в браузер-пейне, попросить пользователя залогиниться самому
  через Google, затем `javascript_tool` → `fetch(API, { headers:
  { Authorization: 'Bearer ' + localStorage.getItem('traty-token') } })`
  прямо из вкладки — токен никогда не покидает браузер пользователя, а
  каждая запись идёт через настоящий `POST /api/expenses` (валидация,
  зеркалирование в Google Sheet и т.д.), просто с явным `created_at`.
- **Локальный dev-сервер (HMR, реальный React-стейт), но с ПРОД-данными** —
  для правки, которая слишком завязана на `App.jsx`-стейт/несколько
  компонентов сразу, чтобы городить `test-X.html`-заглушку (например тумблер
  «Только мои», фикс шторок). Три шага, все временные — не коммитить:
  1. `frontend/vite.config.js` → добавить `server.proxy: { "/api": { target:
     "https://expense-web-peo6.onrender.com", changeOrigin: true } }`
     (прокси на уровне Vite-сервера, не браузера — CORS не участвует).
  2. `frontend/.env.local` → `VITE_API_URL=http://localhost:5173` (ВАЖНО:
     не пустая строка — `api.js` фолбэкается на `localhost:3001`, если
     `VITE_API_URL` falsy; нужен САМ localhost:5173, чтобы запросы были
     same-origin и прокси их подхватил).
  3. Токен между вкладками: скопировать `localStorage.getItem('traty-token')`
     из уже залогиненной прод-вкладки, `localStorage.setItem(...)` в
     localhost-вкладке (localStorage не расшарен между origin), затем
     `navigate` туда же ещё раз — токен валиден, т.к. JWT проверяется по
     подписи, а не по origin.
  После теста — `git checkout -- frontend/vite.config.js` и `rm
  frontend/.env.local` (оба в `.gitignore`, но `vite.config.js` НЕТ,
  случайно закоммитить прокси-таргет легко). Дальше обычный React DevTools/
  console.log-дебаг, а не подмена fetch — так ловили, что `mergeAndSet`
  реально фильтрует по `onlyMine`, и что фикс scroll-chaining не ломает
  свайп-закрытие (синтетические `TouchEvent`/`Touch` с `dispatchEvent`,
  проверка `event.defaultPrevented`).

## Google Sheets: очередь синхронизации + инцидент invalid_grant (2026-08-28)

**Симптом**: пользователь заметил, что часть трат есть на сайте, но не в
Google Sheets (и наоборот — удалённые с сайта иногда оставались висеть в
таблице).

**Первопричина синхронизации в принципе**: `appendExpenseRow`/
`updateExpenseRow`/`deleteExpenseRow` (`services/sheets.js`) вызывались
без `await`, ошибка ловилась и уходила только в `console.error` — ни
ретраев, ни какой-либо видимости с сайта. Единичный сбой Google API
(rate limit, протухший токен, рестарт процесса Render посреди запроса)
терял строку навсегда, без следа.

**Фикс — надёжная очередь**, теперь постоянная часть системы:
- Таблица `sheets_sync_jobs` (`db.js`) — по одной задаче на `expense_id`
  (уникальный индекс, `ON CONFLICT` схлопывает более раннюю ожидающую
  задачу в свежую, если трату отредактировали/удалили до того как она
  успела синкнуться).
- `services/sheetsSyncQueue.js`: `enqueueSheetsSync()` кладёт задачу
  (быстрый INSERT, вызывается `await` прямо в роуте — `routes/
  expenses.js`), фоновый `processSheetsSyncQueue()` тикает раз в 20с
  (`server.js`), экспоненциальный backoff до 30 минут при ошибке,
  таймаут 45с на джобу (`withTimeout`) — без него один зависший запрос к
  Google API мог бы заморозить весь воркер навсегда (флаг `running`
  никогда не сбросился бы).
- `services/sheets.js`: `appendToOne` теперь идемпотентен (проверяет
  `findRow` перед записью) — иначе ретрай уже успешного таргета в
  шаренном кошельке (Семья/Бизнес/Ремонт мирроятся в ОБА аккаунта
  отдельными вызовами) задваивал бы строку.
- `GET /api/expenses/sheets-sync-status` + строка «Синхронизация с Google
  Sheets» в Настройках → Аккаунт (`SettingsSheet.jsx`) — красным, если
  что-то не синкается 5+ попыток подряд. Это теперь единственный способ
  узнать о сбое без ручной сверки — использовать его первым делом, если
  пользователь снова пожалуется на расхождение.

**Реальный триггер инцидента — не баг очереди, а протухший OAuth-токен**:
`invalid_grant` у ОБОИХ аккаунтов (сначала у Есенжана, потом отдельно у
Дарии — общие кошельки пишутся в обе таблицы независимо, так что один
протухший токен ломает только половину). Причина — Google Auth Platform
проекта `adept-parsec-500611-h1` стоял в статусе **Testing**, а Google
жёстко убивает refresh-токен через **7 дней после выдачи** для
приложений в этом статусе — независимо от активности. Обычный релогин
это лечит (при логине всегда `prompt=consent`, значит новый токен), но
ненадолго — через 7 дней тот же токен снова протухнет, ЕСЛИ статус
остался Testing.

**Настоящий фикс**: перевели Google Auth Platform → Audience → Publish
app → **Production**. Для этого потребовалось: 1) на вкладке Branding
заполнить Application home page + privacy policy link (пустая ссылка на
политику конфиденциальности блокировала кнопку публикации) — сделали
`frontend/public/privacy.html`, задеплоено на
`https://expense-web-eosin.vercel.app/privacy.html`; 2) добавить
`expense-web-eosin.vercel.app` в Authorized domains (до этого там был
только домен бэкенда `expense-web-peo6.onrender.com`). После Production
7-дневного лимита больше нет — токен живёт, пока не отозван вручную, не
сменится пароль Google-аккаунта или токен не простоит без использования
6+ месяцев. **Это не косметика — если статус когда-нибудь снова окажется
Testing, баг вернётся ровно в том же виде.**

**Диагностика без доступа к логам Render** (Claude не может залогиниться
на сайт — только настоящий Google OAuth): временно добавляли в
`/api/health` (он и так публичный, без авторизации) снимок
`sheets_sync_jobs` — `id, expense_id, kind, attempts, last_error,
age_seconds`. Так нашли точный текст `invalid_grant` вместо гадания.
Убрали сразу после диагностики — не оставлять такое в проде дольше, чем
нужно для одного разбора.

**Как сверяли, что именно пропало** (без доступа к БД/логину): попросили
пользователя выгрузить CSV через Настройки → Экспорт (CSV) на сайте —
это готовый список всех его записей (id, дата, кошелёк, категория,
сумма, заметка). Сверили построчно по `id` с реальным содержимым Google
Sheets, которое читается БЕЗ логина через публичный экспорт:
`https://docs.google.com/spreadsheets/d/{SPREADSHEET_ID}/export?format=csv&gid={GID}`
(работает, если таблица расшарена хотя бы на просмотр по ссылке; `gid`
каждой вкладки — открыть вкладку в браузере и посмотреть в URL). Экспорт
с сайта отдаёт «мои записи + все записи в шаренных кошельках» — Личные
чужого аккаунта в него не попадают (приватность по дизайну), так что для
полной сверки личных трат обоих нужны ОБА CSV с сайта И ссылки на ОБЕ
Google-таблицы.

**Бэкфилл найденных пропусков** — разовый паттерн, если понадобится
снова: временный `services/sheetsBackfill.js` с хардкод-списком
`expense_id`, один вызов `enqueueSheetsSync('append', expense.user_id,
expense)` на каждый в `server.js` при старте, задеплоить, дождаться (тик
каждые 20с — если джоба уже словила несколько неудачных попыток и сидит
в затянувшемся backoff, можно форсировать немедленный повтор ещё одним
пустым редеплоем — `enqueueSheetsSync`'s `ON CONFLICT` сбрасывает
`next_attempt_at` на «сейчас»), проверить через тот же публичный CSV-
экспорт, затем удалить временный файл и его вызов из `server.js` —
никогда не оставлять бэкфилл-скрипт в кодовой базе после подтверждения.

### Потерянный job удаления — гонка коалесинга (найдено и починено 2026-08-28)

Симптом: добавили трату в каждый кошелёк и сразу удалили — из всех
вкладок Google Sheets строки ушли, из «Бизнес» осталась. Кошелёк ни при
чём, это чистый тайминг: под гонку попадает та трата, чей `append` в этот
момент летел в Google.

Механика: строка очереди уникальна по `expense_id`, и удаление трата
кладёт в **ту же строку** `kind='delete'` (коалесинг). Если `append` в
этот момент был в полёте, по его завершении `runJob` делал
`DELETE FROM sheets_sync_jobs WHERE id = $1` и сносил только что
поставленный job на удаление. Строка оставалась в таблице навсегда, при
этом в очереди ничего не висело и настройки честно показывали
«Синхронизировано» — то есть баг был полностью невидимым.

Починка: колонка `revision`, инкрементируемая каждым `enqueueSheetsSync`.
`runJob` завершает работу через `DELETE ... WHERE id = $1 AND revision =
$2 RETURNING id` — если ревизия уже другая, job вытеснили, и его надо
оставить следующему тику. Ветка ошибки guard'ится так же, иначе свежий
вытеснивший job наследовал бы `attempts` и бэкофф упавшего (и мог бы
попасть в «Проблема: N» за чужую ошибку).

Та же гонка ломала и правку трат: отредактированная во время `append`
сумма не доезжала до таблицы. Воспроизведено и проверено на pglite
(настоящий Postgres) прогоном реальной очереди со стабом Google.

**Осторожно на будущее:** любая работа с этой очередью, которая пишет в
строку job'а после долгого сетевого вызова, обязана сверять `revision` —
между чтением job'а и записью результата строка могла стать другим
заданием.
